# Native iOS runtime reuse: ownership and accepted baseline

Read-only architecture audit, 2026-09-16. The previous canary is complete and its continuation remains closed. No image, service, VM, account, source, workflow or GitHub state was changed; no tests, guest probes, collection or polling were run. Repository instructions were read from the canonical consumer's AGENTS.md; this is an external analysis document, not a change to that repository.

## Decision

A neutral `uxmaltech-collab/ai-runner-images` repository is a suitable proposed owner for versioned image recipes, toolchain locks, image catalogs and reference acceptance evidence. It should consume the existing template-owned host/executor/guest mechanisms and the existing resolver capability. It should not become another agent framework, control plane, credential broker, host inventory or publisher.

The accepted image `93df87c0…` is an EnviaFlores profile derivative, not an organization-neutral base. It contains the full canonical EnviaFlores resource pack, its hydration closure, and repository-specific protected journey descriptors. Reuse its proven mechanisms and compatible toolchain inputs, but do not relabel that same image as a cross-organization image. A neutral toolchain base plus a pack-pinned organization/profile derivative is the compatible separation. A different design that injects a pack into a neutral image would require an explicit, reviewed adapter contract; no existing arbitrary mount/injection API is established here.

The resolver and `create-journey` remain the existing agent and capability. Flutter support belongs in the native platform/toolchain recipe and app build/test adapter. A Linux Dockerfile cannot supply the macOS/Xcode execution that this iOS path requires. Ordinary resolve/review currently remain on the separate Linux SwiftLint profile through an existing command-to-runner mapping; that is not evidence of Flutter or native e2e capability for those commands.

## Existing interfaces worth preserving

The native catalog declares `backend: macos-tart`, `image_build`, capabilities, immutable image digest binding and repository/profile identity. The sidecar maps `create-journey` to that native profile while retaining the same repository agent, Codex engine and shared account. See the [native catalog profile](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/runners/catalog.yaml#L133) and [sidecar routing](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/workspaces/github-codex-runner/sidecars/storefront-ios/manifest.yaml#L5).

`prepare-ios-journey-image.py` composes reviewed offline payloads into a schema2 native manifest. It checks complete canonical pack/templates checkouts and installed CLI source/dependency closure, then delegates to the protected image installer. It does not itself boot, finalize or admit an image. The existing installer exposes plan/stage/finalize/status and bounded stage recovery; host-owned reboot/session proof and admission remain distinct operations. Preserve that source→composition→guest stage→reboot/finalize→admit/bind chain, with reusable receipts for unchanged bytes. Current final image updates used a stopped derivative and component-preservation receipts; those task-scoped adoption helpers are not yet a generic public image-management API.

The host adapter exposes plan/apply/configure/activate/rehearse/bootstrap/reconcile/recover/rollback/status. Initial installation and service activation are deliberately distinct; keychain bootstrap uses the real startup context. A recipe should call supported owner operations, not duplicate account edits or configure a second SSH service itself. Reference [host adapter](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/skills/host/github-runners-host-sre/scripts/macos-host.py#L1885).

Exploration and final validation are separate bound jobs. The first invokes the ordinary resolver after building/installing the app; the second binds the delivered flow hash and a fresh commit, omits the launcher and excludes engine credentials before loading/staging them. Preserve this separation for Flutter. Keep configuration byte-preserving and repository/environment-scoped; issue data should not select arbitrary tools/accounts/platforms. The native app supplies observed UI selectors and replay data, not new operational authority.

## Specific coupling that must be addressed

1. **Image recipe and derivative identity.** `prepare-ios-journey-image.py` selects storefront-ios paths, `agent(ROOT, 'storefront-ios')`, the EnviaFlores canonical pack origin and Python3.12.14; its descriptors embed the app repository/profile and protected pack paths. Generalize reviewed recipe inputs in the owning source, then move/reference neutral recipe data. Do not merely rename directories. [Recipe source](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/runners/scripts/prepare-ios-journey-image.py#L19).
2. **Driver contract.** `journey_jobs.driver()` requires exactly `enviaflores/ef-storefront-ios`, `resolver-storefront-ios-native`, `ios-maestro` and `scripts/validate-maestro.py`. This is current consumer-owned code, not an already generic API. Introduce an authenticated declared build/test adapter identity with strict profile/repository/source binding; reusable shared logic can then move upstream deliberately. [Exact checks](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/runners/lib/journey_jobs.py#L232).
3. **Tool schema is closed.** Native installer `TOOL_ARGS` contains xcode/java/maestro/git/runner/engine/runtime/python/simulator and rejects extra keys at line350. Guest configuration likewise requires exact VERSION_ARGS plus simulator. Flutter cannot simply be added as another tools key. A declared capability/tool-extension contract and matching probe/receipt support belongs in templates, or an explicit separately validated payload/adapter contract must be designed. Current tree-payload support alone does not attest Flutter functionality. [Installer schema](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/runners/control-plane/macos-image/prepare-image.py#L293) and [guest tool contract](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/runners/control-plane/runner_control_plane/tart_guest.py#L183).
4. **Pack identity and image namespace.** Organization, pack origin, runner sentinel and image prefix already have an explicit template `pack-profile` block. Shared `tart_contract._image()` itself accepts generic registry/repository@digest; no literal IMAGE_PATTERN was found in the canonical runners/CLI/host-script tree. EnviaFlores-only IMAGE_PATTERN values in checkpoint adoption/observer helpers are task-specific and should not be promoted as generic APIs. CLI runtime.py still hardcodes the EnviaFlores canonical pack origin in source-checkout handling. Parameterize this deliberately; do not claim an unrelated shared image validator needs widening. [Identity block](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/runners/control-plane/runner_control_plane/profile.py#L11), [generic image syntax](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/runners/control-plane/runner_control_plane/tart_contract.py#L130), [CLI origin binding](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/cli/ai-repo-resource/src/ai_repo_resource/runtime.py#L410).
5. **App-specific staging and data.** Environment preparation identifies the EnviaFlores app/staging; the repository module requires location/catalog links and a product name in the flow. Those are retail-app semantics, not portable Flutter inputs. A Flutter app declares its own build configuration and required smoke/discovered data, preserving the same source/hash/replay discipline.
6. **Publication destinations.** `journey_evidence.py` fixes `enviaflores/collab-resources` and an EnviaFlores repository regex; native publisher/orchestration fixes app identity and `journeys/ef-storefront-ios/...`. Use an approved organization/repository publication declaration with the same append-only, sanitization, immutable-readback guarantees. Keep the external publisher out of the guest and out of the generic toolchain base. [Publisher binding](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/runners/scripts/publish-native-journey.py#L46).
7. **Documentation/version drift.** Current integration/image prose still mentions control-plane0.7.0 and CLI2.10.1 although the accepted pins are0.9.9 and CLI3.0.2. `image-build.json` keeps admission_enabled:false as a source preparation declaration while actual host admission is evidenced separately. New catalogs must derive versions/readiness from pins and receipts; copying those prose values or interpreting that field as current host state is incorrect.

## Minimal extraction sequence, not an implementation claim

First specify ownership and a data-only recipe/catalog schema in the proposed image repository. Pin the existing native components and record the accepted EnviaFlores derivative as a reference consumer, without publishing host secrets or implying cross-org acceptance. Parameterize the identified consumer-owned coupling and submit any tool-schema/host/guest changes to templates, followed by consumer pin adoption. Keep the ordinary resolver CLI and capability intact; upstream genuinely shared logic once, rather than forking it into the image repository.

Then define a neutral macOS/Xcode toolchain base and a locked profile derivative with explicit pack/driver provenance. Choose the first Flutter app's Flutter/Dart/plugin dependency closure and build/test adapter. Prove build, effective staging configuration, isolated simulator, observed UI semantics, flow delivery, clean-commit rebuild/replay without agent auth, external byte-verified publication and cleanup on that app. No Flutter SDK version, dependency backend, model/account change or new test command is assumed here. `test-e2e` would be a proposed capability, not an already implemented command demonstrated by this baseline.

The latest upstream repository catalog and official Flutter requirements are handled by the parent analysis. This document establishes the locally evidenced native baseline and concrete ownership seams; it does not create the proposed repository or promote newer upstream main.

## Follow-up: fresh-host SSH repeatability and CLI ownership

This append preserves the original report (SHA-256 `419f085d569e22853d6132bd42d0be698ea572832dab4c95e8d9d5ee0feafe0e`) and adds two bounded source/receipt checks. No live host state, credentials, network, service or image was inspected or changed.

**The accepted deployment includes a native SSH service-ACL repair that the reusable installer still does not implement.** Unit61847's retained original log identified `pam_sacl` rejecting the dedicated account's SSH service access. Its local PAM account check returned7 before repair and0 after adding only that account to the existing `com.apple.access_ssh` group through Darwin's `dseditgroup`. The original handoff explicitly states that no installer SACL provision/preflight operation existed and that this future capability belongs to template `sre/github-runners-host-sre/macos-host.py` followed by consumer adoption.

The implementation checks PAM-compatible shell, dedicated account/home and nonadministrator group membership; it has no `dseditgroup`, `com.apple.access_ssh` or SACL reconciliation/preflight implementation. This conclusion is about those local canonical objects; it does not assert the contents of a newer remote templates HEAD that was not fetched for this review.
