## Result

Neither target currently has an agent entry, exclusive sidecar, runner profile, manifest or command routing in this accepted pack. There is also no Flutter/Dart SDK constraint or Lastmile package-test contract in the inspected tracked framework surfaces. Existing iOS profiles cannot be assigned to these repositories unchanged.

The appropriate reuse is the existing resolver/hydration and journey lifecycle, plus the demonstrated native macOS execution substrate. The new host app needs an explicitly declared native Flutter-capable derivative and app-specific build/test contract. It does not need a second persona dedicated only to create-journey. A package's ordinary unit/widget/static tests may use a declared Flutter Linux profile when its own contract permits; an iOS plugin/integration/UI acceptance through the host app requires the native profile. No existing profile currently establishes either Flutter toolchain.

## Toolchain and test boundaries

The accepted native image proved Xcode26.5/build17F42, iOS26.5 simulator, Maestro2.10.0, Java17.0.20.1+1, Python3.12.14, the ordinary CLI3.0.2 and authenticated Codex. It did not prove Flutter/Dart, a Flutter dependency cache, plugin integration, CocoaPods/Ruby or a Flutter project build. Do not choose those versions from the Swift canary. Derive the SDK/version constraints, plugin dependency mechanism, flavors/entrypoints and required tests from the Lastmile app/package sources and their lockfiles; preserve that exact dependency closure in the recipe and acceptance evidence.

The template-owned native installer currently rejects arbitrary extra tool keys: [prepare-image.py lines51–54 and350](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/runners/control-plane/macos-image/prepare-image.py#L350). The guest has a matching exact tool set. Flutter needs the previously identified declared capability/probe extension or a specifically verified payload/adapter contract; adding a JSON key alone is insufficient. Native toolchain changes belong to recipe/template owners. Host account/SSH/bootstrap prerequisites remain host-owner operations and must not be duplicated in a Flutter setup script.

`storefront-core-pkg` is not a reusable Dart package-test registration. Its [package conventions](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/skills/repo/storefront-core-pkg/references/package-conventions.md) describe PHP/Laravel/BOUI, Composer and `vendor/bin/phpunit` with Orchestra Testbench. Its linked expertise must not be transplanted into lastmile-drivers-pkg-flutter merely because both are packages. The generic [_template package reference](https://github.com/enviaflores/ai-repo-resources/blob/3a3e163793d85a2110a7de5098ffe2a2f90b2f3b/skills/repo/_template/references/package-conventions.md.tmpl) itself requires explicit applicability; stack similarity does not register a repository.

The application supplies the runnable iOS host. For package changes exercised through it, the execution identity must bind the host-app commit and the exact package source/dependency resolution used by that build. The current journey plan binds one repository/app commit and one app-owned flow; it does not establish an existing cross-repository Lastmile package substitution API. Root's target-repo review must determine whether a package example app, host integration, dependency override or published package revision is the supported test route. No such route or passing command is invented here.
