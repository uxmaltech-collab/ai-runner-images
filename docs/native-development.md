# Autonomous native development

Use this procedure for image/runtime development and mechanical canaries. Use
qualified production adoption for a known generation. These modes preserve the
user's authorization, installed host authority, live work and credential scope;
a different mode does not authorize a new service, account or execution path.

## One native owner, one working loop

Give the native operator the affected behavior and the full mechanical target,
not one checkpoint at a time. Its input consists of the retrievable release,
recipe and pack identities, retained parent, existing host binding and execution
authority, neutral fixture, expected outputs and cleanup, plus the already
approved repair/publication scope. Include the actual failing stage and known
limitations. Never transfer secret values or the GitHub App private key.

The native operator owns build or component update, disposable execution,
inspection of failures, fixes in their canonical owners, affected local checks,
authorized source promotion, and another execution. It does not wait for Linux
to discover the next native failure or acknowledge a file transfer. Follow an
explicit requirement to distribute runtime changes through immutable releases;
coordinate one release writer so two hosts do not publish the same version.
Runtime changes belong in Collab CLI, image mechanics/fixtures here, declarative
bindings in their pack. Do not fork the runtime into a recipe or pack script.

Reuse verified parent/toolchain layers. Requalify only the changed dependency
closure. A documentation or instruction edit does not rebuild an image or update
an application workflow. Preserve exact artifact identities; when a contract
couples whole source commits, state that limitation instead of claiming reuse
that the current implementation cannot support.

## Mechanical target in a disposable clone

Run under the same unprivileged identity, HOME, PATH, Python and GUI/session
context as a real job, through the existing image/session owner. Keep the sealed
parent and live service unchanged. Exercise the applicable stages in one loop:

1. Clone and boot; prepare the native session and confirm its real user context.
2. Load the selected published runtime/providers and declared guest entrypoint;
   hydrate the intended data-only pack and declared references, including Archify
   when that profile uses it. Use the selected release's implementation.
3. Execute a small neutral fixture through the real applicable runtime/stack
   entrypoint. Observe exit status and output collection, not just imports,
   version flags, health or a deliberately rejected envelope. A local protocol
   fixture is labeled synthetic; it is never a GitHub run, lease or JIT receipt.
4. Exercise the actual changed tools. For a compiler/toolchain change, compile
   its neutral fixture; for UI capability, install/launch and assert a minimal
   app in its isolated simulator. Do not make unrelated app builds or all
   engines mandatory for a host-only change. Engine launch without its existing
   job credential does not establish an authenticated model session.
5. Collect the bounded output, finish or cancel the owned process as applicable,
   stop/delete the disposable child, and verify owned process/VM cleanup. Test
   recovery of the observed failure in that same isolated fixture; never induce
   destructive faults against live work.

The mechanical result names its runtime, recipe, image, pack, fixture, stages,
actual outputs and cleanup. Preserve failures. An unexercised stage stays
unverified. Missing prose, a handoff acknowledgment or unrelated debt is not a
reason to stop a runnable development fixture. Do not mark production ready
until its separate acceptance has run.

## Existing tools and current coverage

`python3 scripts/build-images.py plan/build` and the native backend remain the
construction entrypoint; see [build instructions](build-images.md). The existing
`recipes/macos/qualify.py` runs a disposable nonadministrator session, tool checks,
real SwiftLint fixtures and cleanup. The Flutter reference separately exercises
a real neutral Flutter build and Maestro. These are useful scoped results.

The current session fixture loads six historical Templates modules via
`recipes/qualification-session/module-lock.json`. It does **not** demonstrate
that the current Collab release can hydrate and execute its entire guest path,
that host upgrade/rollback works with installed history, or that a GitHub job
can deliver. Do not credit historical session success to another runtime.

A reusable current-runtime mechanical fixture is therefore an implementation
gap, not a missing receipt. Put neutral fixture/orchestration in this repository,
using the published CLI's real typed APIs; put missing execution/recovery
capabilities in CLI. Extend the existing build/qualification entrypoint instead
of inventing a checkpoint-only runner or configurable arbitrary command loader.
Until implemented and exercised, report the covered stages and this exact gap;
it is not a reason to block an otherwise authorized real development canary.

## Central integration and production adoption

Linux owns webhook acceptance, queue admission and real GitHub JIT through its
existing control-plane authority. The Mac never needs the App private key.
If the only way to exercise a boundary is an actual central request, let Linux
send that request while the Mac owns diagnosis/repair of the native leg; no
per-stage handoff or redundant observer is needed. Reconcile an uncertain run
before retrying, within the user's authorized retry scope.

Mechanical qualification does not establish bot acceptance, remote branch,
opened/assigned PR, business behavior or production validation. The public
canary owner proves those on the same actual run after controlled adoption.
Host upgrades also need an isolated lifecycle rehearsal covering the changed
forward path, observed failed state and recovery; an image fixture does not
replace this separate host behavior. Keep production source and service changes
with their installed authorities and drain active jobs before replacement.

## Repeated failure and research

After three failed attempts at the same operation, investigate before the next
execution; do not reset the count for a new image tag, release, host or session.
Use the existing task record, inspect the first error and actual runtime inputs,
consult primary documentation/source, and explain the changed diagnosis and
next observable test. Research earlier for deterministic failures. This does
not increase an existing retry limit or authorize replay of uncertain effects.
See the [GitHub runner research](github-runner-research.md) for the operational
facts behind this division of work.
